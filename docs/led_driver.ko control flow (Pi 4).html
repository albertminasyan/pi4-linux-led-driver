led_driver.ko on Raspberry Pi 4: how control flows

Module led_driver.ko creates /dev/led0; writing '1' or '0' to it drives GPIO17. Pick a view, then press Next to step through it.

If any call in led_init fails, it undoes what it already did and returns an error. The kernel then abandons the load and led_exit is never called.

echo -n 1 | sudo tee /dev/led0 and led_app 1 differ only in who calls write(). echo writes into a pipe; tee (root) opens the device and makes the call that reaches the driver. Try sudo strace -e trace=openat,write tee /dev/led0 to see it.

rmmod fails with “Module is in use” while any process still has /dev/led0 open, because the reference count is not zero.

Kernel side (EL1), module loaded

struct module: name, state, refcount, pointers to init and exit
.init.text: led_init(). Freed when init returns 0, so never call it again.
.text: led_write(), led_read()
.exit.text: led_exit(). Kept, because rmmod needs it.
.rodata: led_fops (const table), strings “led”, “led0”, log messages
.data: led_lookup (the kernel keeps a pointer to it until removed), led_misc
.bss: led_gpio pointer (zero, set by led_init)
kernel heap: objects owned by gpiolib and the misc subsystem (gpio_desc, device entry), plus one struct file per open
kernel stack of the calling task (about 16 KB): char c in led_write, return addresses. Exists only during the syscall.
GPIO registers (MMIO, mapped by pinctrl-bcm2711): GPSET0, GPCLR0, GPLEV0, GPFSEL1

User side (EL0), process led_app

.text: main() of led_app
.data / .bss: none of note
heap: unused by led_app
shared libraries (mmap region): libc, with the write() wrapper that executes svc
stack: fd, argc, argv; the string "1" that argv[1] points to sits at the top
copy_from_user(&c, buf, 1): the driver copies one byte from the user buffer (argv[1]) into c on its kernel stack. The kernel never dereferences the user pointer directly. led_read does the reverse with copy_to_user.

Compare with Arduino: there .init0 … .init9 run once in flash and stay. Here .init.text is returned to the kernel after load, and the rest stays until rmmod.
